# 测试与 AI 验收规范

维护日期：2026-10-22。适用于当前工作区功能，包含尚未提交的小组与局域网同步。用例定义、自动化覆盖、执行结果分别维护，不能互相代替。

场景验收包的保存观察须在应用初始化完成、无保存进行中时开始；重复导入完成后结束并记录接口调用、成功和失败计数。观察只在当前进程内有效，重启清除；不展示业务内容。故障注入前失败仍计一次接口失败，不等于 SQLite 写入。

主题偏好故障必须使用独立主题仓储控制，不能借用业务保存开关。场景包的保存失败与显式释放延迟只用于验证产品原入口；控制不持久化，不输出主题值或业务内容。不得通过强制重挂载应用丢弃草稿来制造读取失败；未提供安全读取故障入口时，真实界面分项记为 NOT_RUN，单元证据不能替代。

主题读取失败冷启动验收只用于 scenario 包：先退出所有编辑页并确认保存完成，保留一个非默认主题；结束进程后用精确启动地址 `sprout-scenarioacceptanceqa://acceptance/theme-read-failure?once=1` 首次启动。须确认本进程 load-fail 已命中、回退及原设置错误提示；先不选择主题，普通 Launcher 冷启动核原偏好仍在，再单独测试主动重选恢复。暖链接不应重新待命或重挂应用，故障标志不得持久化；不将此受控接口前失败等同介质损坏或坏原文覆盖测试。

## 需求到验收的流程

1. 明确需求、入口、验收标准与影响范围；读取当前 diff，保留无关工作。按覆盖表选择直接影响模块及依赖模块。
2. 修改前运行相关已有测试，记录基线；新增用例使用新编号，缺陷增加可复现步骤和回归用例，规则改变时更新旧预期并说明原因。
3. 实现并补充有意义的自动化测试；优先验证业务结果、边界、拒绝操作不变异及保存失败原子性，避免仅复制实现逻辑。
4. 修改后先运行针对性测试，再运行完整质量检查；按功能用例执行冒烟与影响回归。涉及平台 API 时补原生设备验证。
5. 另开独立 verifier/code-reviewer 审核 diff、用例及证据；失败继续修复并重跑相关检查。文档变更可做链接、编号、覆盖完整性与格式验证，无需为文档编写产品单测。
6. 填写验收记录：实际结果、命令退出码、证据、缺陷、未执行项及原因。回写用例库、覆盖表和必要的应用说明。未执行项不能标记为通过。

## 用例维护约定

用例编号一经分配保持稳定，不按显示顺序重新编号，不复用已停用编号。删除功能时保留停用记录及原因。当前用例库是可执行规范，不代表已逐条执行。

- P0：数据正确性、核心闭环、重复消费与跨账户隔离。每次功能改动必须回归受影响 P0；发布执行所有 P0。
- P1：常用功能、重要异常、边界、持久化。改动模块及其依赖模块执行；发布全量执行。
- P2：扩展展示与兼容性。按影响范围执行，发布时记录设备矩阵覆盖情况。

执行状态只使用 `PASS / FAIL / BLOCKED / NOT_RUN / N/A`。`N/A` 必须有不适用原因；`BLOCKED` 写明缺少的运行条件。参数化用例的每个输入、平台和设备分别记录结果，不能用一个成功样本代替整组。

使用 Node 24，项目根目录运行 npm 脚本，依赖以锁文件为准。先检查 `node --version`；当前宿主默认 Node 18，工作区已验证可用的 Node 路径是 `/Users/lin/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node`。该路径是本机示例，其他环境按实际 Node 安装位置调整。

```

已有 `node_modules` 时先使用现有依赖；需要重装时使用 `npm ci`。不要修改锁文件来绕过测试失败。格式检查排除 Android 的 `build`、`.cxx` 和 `.gradle` 生成缓存，不排除 Android 源码；应如实记录源文件问题，不能用局部检查替代全量通过声明，也不为通过检查删除生成缓存。

针对性执行示例（使用已安装的 tsx）：

```

涉及打包入口、依赖或跨平台代码时，按影响范围执行：

```sh
npm run export:web
npm run export:android
npm run export:ios
```

`export:*` 仅验证资源打包，不证明安装、启动或真机功能通过。UI 开发入口为 `npm run web`（localhost:8082）；本次未找到项目提供的浏览器自动化 runtime、E2E 脚本或配置。后续 Web UI 自动化只能使用项目提供的 runtime，不得用外部浏览器驱动或 computer-use 绕过。runtime 缺失时标记 BLOCKED 并记录需要的配置；同一次 runtime 异常时尽量继续探查其他可达用例路径。

测试必须使用独立存档/浏览器配置或测试设备，不清除用户现有数据。Web 业务 key 为 `sprout-native-sync-v1`，原生数据库为 `sprout-native-sync-v1.db`；主题与小组视图另存设备偏好。不要让多个可写标签页共享同一测试存档。演示数据会写入真实存档并参与统计，不是可随意清除的 mock。

### Android 专用验收包

已有 acceptance 存档需保留而需验证首次导入时，可构建 `npm run build:apk -- --fresh-acceptance`：独立 ID `com.smallsteps.checkin.freshacceptanceqa`、标签「小步新验收」、协议 `sprout-freshacceptanceqa`，禁备份，使用共享验收界面的独立 production 入口，禁用局域网监听及手动同步。普通验收包不受影响。安装前检查该 ID 尚未被占用；一旦产生存档，重装不能视为全新存档，不可清除或卸载以重做。与其他隔离选项互斥，实际产物和设备冷启动及网络隔离须单独验证。

当现有 QA 包已有需要保留的存档时，可用 `npm run build:apk -- --acceptance` 构建第三个独立包 `com.smallsteps.checkin.acceptanceqa`（「小步验收」，协议 `sprout-acceptanceqa`，禁备份）。该选项与 `--qa` 互斥，产物带 `-ACCEPTANCE`，不覆盖历史 APK。安装前先核对该应用 ID 未被既有验收存档占用；有存档时保留，不把再次安装当作空存档测试。

此 variant 非 debuggable，内嵌 production JS bundle（`devEnabled=false`）和独立 `acceptance/index.tsx`；不可改为开发 bundle，Expo 开发消息通道会拒绝嵌入环境并导致启动失败。验收入口在根组件注册前显式开启本进程的演示预览许可，设置页在渲染时读取；普通 QA/release 使用原入口，许可默认关闭，不引入验收控制模块。只有专用包提供可隐藏、左右移动的验收控制按钮；隐藏后重启恢复。初次启动不自动造数据，先验证无组空态，再在原「更多 → 设置 → 添加演示历史」入口显式确认，执行 DEMO-005。不得输入真实组邀请码或主动同步演示组至其他应用。

验收面板可显式待命下一次业务保存延迟八秒或一次性失败，关闭面板后仍待命；可取消，重启失效。应从原业务界面触发并核对命中状态；处理中不能重新待命。失败为写入前受控抛错，不是 SQLite 故障。面板条件挂载原生 Modal，真机应另查返回键及无障碍隔离。

VIEW-014 受控失败步骤：奖券页先切「只看自己」→ 验收控制开启下一次看全组保存失败 → 返回今日小组动态点击成员。预期保存失败并留在原页；开关自动消耗，再次点击可正常保存及导航。控制仅包装查看偏好仓储方法，在调用真实保存前抛错一次，不包装业务仓库、不写入故障标记；取消或进程重启后失效。此结果只能证明受控失败分支，不能声称真实 SQLite I/O 失败通过。

专用包仍须核对实际 APK 包名、标签、签名、禁备份、内嵌 bundle、非 debuggable；分别验证无 Metro 的冷启动、控制消耗/取消/重启失效及原功能。新协议仅隔离系统分发，不代表已完成应用内深链路由验收。

日期边界优先以业务函数注入时间验证，避免修改工作设备时钟。界面确需边界测试时使用隔离设备，记录时区、当地日期和实际到期时间；不得按 UTC 日期代替本地日/周。双设备场景各自保留独立身份，不记录完整邀请码、口令、原始业务存档或头像数据到公开报告。

## 冒烟与回归门禁

### Android 独立排行夹具包

成员副本保护专用使用 `npm run build:apk -- --peer-protection`，目标仍是已有 `com.smallsteps.checkin.fixtureqa`，并非新的空存档。独立entry仅对此variant开放原设置演示许可并禁LAN，普通 `--fixture` 入口继续不启用演示。新协议 `sprout-peerprotectionqa` 与标签区分入口，但不隔离同ID数据；覆盖前逐机记录版本、签名、主题及非空本机/成员基线，同签名更高code安装，不卸载、清档、降级或复制存档。

专用准备必须先校验精确夹具组与已有合法10成员副本、无待离组、无个人演示标记及新身份冲突；显式二次确认后仅追加一个含资料、任务、3打卡和1永久券的合法新成员journal，经原store事务保存。不重造旧peer链，不提供通用导入或重置，重复准备应拒绝且不保存。本机资料若为空须经原资料UI显式保存。先核原业务保留，再从原设置确认添加个人演示，核既有成员/原资料业务保留，重启后重复。进程内基线比较与接口计数不是私有SQLite逐表审计，不输出完整副本、密钥或outbox内容；实际APK与设备结果另记。

使用 `npm run build:apk -- --fixture`（与 `--qa`、`--acceptance` 互斥），包名 `com.smallsteps.checkin.fixtureqa`、标签「小步夹具」、协议 `sprout-fixtureqa`、禁备份，产物 `-FIXTURE` 不覆盖旧包。首次安装前核对该包没有需保留的旧夹具存档；升级不清空已有夹具，禁止用卸载或清数据重跑。普通/QA/验收入口依赖图不引入 `fixture/`，夹具入口也不启用验收故障控制或演示导入。

夹具入口复用原有 App、Provider、SQLite 和导航，仅通过 `lanEnabled=false` 禁自动监听与手动交换，点击同步明确提示禁用，不改系统网络、不伪造同步成功。默认入口仍开启原有网络行为。这是离线副本夹具，不能当作双设备同步证据。

首次进入不生成数据。显式打开「夹具」面板→「准备夹具小组」→返回今日检查 VIEW-004/010 有组无副本；再打开面板→「追加排行夹具…」→确认。每步经领域函数和 `store.run` 原子保存，只接受默认业务与固定夹具小组；已修改过任务/资料/规则、打卡、奖券、其他组及重复夹具均拒绝保留，不提供 JSON 导入、清空或恢复。

追加后 11 位当前成员次数为 11 至 1、无并列，本周合计 66 条（65条今天、1条本周一，超过首屏30条）。周一没有同周其他过去日期，拒绝添加，需周二至周日执行。默认 `task-1` 在各成员独立，最后一位只有本周一那条记录且任务已删除，形成真正的单条日期组。到今日小组动态分别检查第 10/11 名、12dp 名次头像间距、长昵称、单条日期节点与分页、成员只读。字号 1.0/1.5 的系统切换、原始截图和实际渲染结果分别记录；Node 夹具验证不算 UI 通过。最后通过原日历选上一年 12 月 31 日、本年 1 月 1 日，在「夹具·排行与跨年补卡」任务真实补卡，检查所属日期/周及操作时间；不修改系统时钟。两天是否同周以实际本地周一规则判断，不能假定跨年必跨周。

最小冒烟按用例库中“冒烟顺序”执行：启动与导航 → 新建任务与打卡上限 → 本周兑换 → 用券与重复使用保护 → 里程碑首次发券与去重 → 重启持久化。涉及小组时追加双设备同步及成员只读隔离；涉及赠券时追加两身份领取与回执闭环。

发布前执行所有 P0/P1，并覆盖 Web、Android、iOS 的适用项。设备受限时记录未覆盖平台，不能据此声称全平台验收。375/390 窄屏、横屏、大字号、键盘、相机权限和后台恢复属于交互验收，静态布局断言不能代替。

完成条件：需求对应的用例已维护；相关自动化及实际交互有证据；没有未解决的相关 P0/P1 失败；独立复核完成；已知基线失败单独列出且未新增失败。缺少关键原生或 UI 证据时只能声明“代码/自动化验证完成，功能验收待补”，不得声明整体验收通过。既有失败也不能无说明地忽略或通过放松断言消除。
